Module 5

⌨️ Claude Code

Claude Code amène Claude là où le code vit vraiment : dans votre terminal, votre IDE et votre dépôt. Il lit vos fichiers, écrit des modifications, exécute vos tests et corrige ses erreurs. Ce module vous mène de l'installation jusqu'aux hooks, aux sous-agents et à l'automatisation en intégration continue.

Objectifs de ce module
  • Installer Claude Code et mener une première session utile sur un projet réel.
  • Donner à Claude la mémoire de votre projet avec un CLAUDE.md bien écrit.
  • Maîtriser permissions, commandes personnalisées et flux de travail git.
  • Automatiser : hooks, serveurs MCP, sous-agents, mode headless et CI.

🟢 Niveau débutant

1. Qu'est-ce que Claude Code ?

Débutant

Claude Code est l'agent de codage d'Anthropic. La différence avec un chat où l'on colle du code : Claude Code travaille directement dans votre projet. Il n'a pas besoin que vous lui décriviez votre architecture — il l'explore.

Quatre capacités fondent tout le reste :

CapacitéConcrètement
LireOuvrir les fichiers, chercher dans le dépôt, suivre les dépendances, comprendre une convention
ÉcrireCréer et modifier des fichiers, avec un diff que vous validez
ExécuterLancer vos commandes : build, tests, linters, scripts, git
CorrigerLire la sortie d'erreur, formuler une hypothèse, modifier, relancer — en boucle

C'est la quatrième qui change la nature de l'outil : parce qu'il exécute vos tests, Claude Code obtient un retour objectif sur son propre travail. Il ne se contente pas de produire du code plausible ; il vérifie qu'il passe.

Trois surfaces d'utilisation, un même agent :

  • Le terminal : la forme de référence. On lance claude dans un dossier de projet et l'on dialogue.
  • L'IDE : extensions pour les environnements courants — le contexte du fichier ouvert et de la sélection est transmis, les diffs s'affichent dans l'éditeur.
  • Le web et les intégrations : sessions lancées depuis le navigateur ou déclenchées depuis un dépôt (voir la leçon 10).

Les usages qui rentabilisent le plus l'outil ne sont pas toujours ceux qu'on imagine : comprendre un projet inconnu, écrire les tests manquants, faire une migration répétitive sur 60 fichiers, expliquer une régression, rédiger un message de commit honnête. La documentation complète est sur docs.claude.com.

💡 À retenir Claude Code n'est pas « de l'autocomplétion en plus gros ». C'est un collaborateur à qui l'on confie une intention (« ajoute la pagination à cet endpoint et couvre-la de tests ») et dont on relit le travail comme celui d'un humain.

2. Installation et première session

Débutant

L'installation la plus courante passe par npm (Node.js requis) :

npm install -g @anthropic-ai/claude-code

Placez-vous ensuite à la racine d'un projet et lancez la commande :

cd ~/projets/mon-application
claude

Le répertoire courant compte : c'est le point de départ de tout ce que Claude explorera. Lancer claude depuis votre dossier personnel plutôt que depuis le projet est l'erreur de débutant la plus fréquente.

Au premier démarrage, Claude Code vous guide à travers l'authentification : soit avec votre compte Claude (abonnement claude.ai), soit avec une clé d'API de la Console Anthropic. Le navigateur s'ouvre, vous validez, la session est établie. Les identifiants sont conservés localement ; vous n'avez pas à recommencer à chaque lancement.

Vos premiers réflexes dans la session :

CommandeRôle
/helpLister les commandes disponibles — votre point de repère
/initAnalyser le projet et générer un CLAUDE.md de départ (leçon 4)
/clearRepartir d'un contexte vide entre deux sujets sans quitter
/modelChanger de modèle pour la session
/permissionsConsulter et ajuster ce que Claude a le droit de faire

Vérifiez que tout fonctionne avec une demande sans risque : « Décris-moi l'organisation de ce dépôt en dix lignes ». Claude va lister des fichiers, en lire quelques-uns, et vous répondre. Vous verrez au passage les demandes de permission apparaître : c'est normal, la leçon 6 y est consacrée.

⚠️ Prudence Ne lancez pas Claude Code dans un dossier contenant des secrets en clair (fichiers .env, clés privées, exports de base de données). Vérifiez d'abord votre .gitignore et, au besoin, restreignez les accès (leçon 6).

3. Vos premières demandes

Débutant

Commencez toujours par faire lire avant de faire écrire. Une session type sur un projet que vous connaissez mal :

Explique-moi ce que fait ce projet : point d'entrée, principales
couches, et comment on le lance en local. Ne modifie aucun fichier.
Où est gérée l'authentification des utilisateurs ?
Cite-moi les fichiers et les fonctions concernés.
Qu'est-ce qui se passe exactement quand un utilisateur
réinitialise son mot de passe ? Décris le parcours étape par étape.

Ces demandes ne coûtent rien et vous font gagner des heures de lecture. Elles vous apprennent aussi à jauger la fiabilité de l'outil sur votre code, avant de lui confier des modifications.

Passez ensuite à une petite modification, la plus petite possible :

Dans src/utils/dates.js, la fonction formatDate ne gère pas
les dates nulles : elle lève une exception. Fais-la renvoyer
une chaîne vide dans ce cas, et ajoute un test qui le couvre.

Claude proposera un diff : les lignes retirées, les lignes ajoutées. Relisez-le avant d'accepter, avec trois questions en tête :

  1. Le périmètre est-il respecté ? Une modification qui touche cinq fichiers alors que vous en attendiez un mérite une explication.
  2. Y a-t-il des effets de bord ? Une signature de fonction modifiée, un import supprimé, une valeur par défaut changée.
  3. Est-ce que je comprends ce code ? Si vous ne le comprenez pas, ne l'acceptez pas : demandez une explication ou une version plus simple.

N'hésitez pas à refuser et à reformuler. « Non, garde la signature actuelle et traite le cas en amont » est une instruction parfaitement claire, et bien plus efficace que de corriger vous-même après coup.

✳ Le réflexe clé Une demande = une intention vérifiable. « Nettoie le projet » produit un diff illisible ; « supprime les imports inutilisés dans src/, sans toucher au comportement » produit un diff qu'on relit en une minute.

🟠 Niveau intermédiaire

4. CLAUDE.md, la mémoire du projet

Intermédiaire

Un fichier CLAUDE.md placé à la racine du dépôt est chargé automatiquement au démarrage de chaque session. C'est la mémoire durable du projet : ce que vous n'aurez plus jamais à réexpliquer. Un projet sans CLAUDE.md vous fait répéter les mêmes consignes vingt fois par semaine.

Pour en générer un premier jet, lancez /init : Claude explore le dépôt et propose un fichier de départ, que vous corrigez ensuite à la main. Une mémoire se maintient ; elle ne se génère pas une fois pour toutes.

Trois niveaux coexistent : le CLAUDE.md du projet (versionné, partagé par l'équipe), celui de votre compte dans ~/.claude/CLAUDE.md (vos préférences personnelles, tous projets confondus), et des CLAUDE.md de sous-dossiers pour les monorepos. Un exemple complet :

# CLAUDE.md

## Le projet en trois lignes
API de facturation pour PME. Node 20 + TypeScript + Fastify,
PostgreSQL via Prisma. Le front est un dépôt séparé (`facturation-web`).

## Commandes
- Installer : `pnpm install`
- Lancer en local : `pnpm dev` (nécessite `docker compose up -d db`)
- Tests : `pnpm test` — un seul fichier : `pnpm test src/facture.test.ts`
- Lint + format : `pnpm lint` et `pnpm format`
- Migration : `pnpm prisma migrate dev --name <nom>`

## Architecture
- `src/routes/` : définition des routes HTTP, aucune logique métier
- `src/domain/` : logique métier pure, sans accès base ni HTTP
- `src/repositories/` : accès aux données, seule couche qui touche Prisma
- `src/lib/` : utilitaires transverses
Règle : une route n'appelle JAMAIS un repository directement,
elle passe toujours par `domain/`.

## Conventions
- TypeScript strict, aucun `any` (utiliser `unknown` + validation Zod).
- Les erreurs métier héritent de `DomainError` (`src/domain/errors.ts`).
- Les montants sont des entiers en centimes, jamais des flottants.
- Nommage : fichiers en kebab-case, types en PascalCase.
- Tests colocalisés : `facture.ts` → `facture.test.ts`.

## À faire avant de proposer un diff
1. `pnpm lint` doit passer.
2. `pnpm test` doit passer.
3. Toute modification de schéma s'accompagne d'une migration.

## Pièges connus
- `docker compose up -d db` doit tourner AVANT les tests d'intégration.
- Le webhook de paiement est rejoué : toute écriture doit être idempotente.
- Ne pas modifier `src/legacy/` : code figé, remplacé au T3.

Ce qui distingue un bon CLAUDE.md : il contient les commandes exactes (copiables telles quelles), les règles non devinables depuis le code, et les pièges qui font perdre du temps. Ce qu'il ne doit pas contenir : un cours sur le langage, la liste exhaustive des fichiers, ou des règles que le linter applique déjà.

💡 Repère Chaque fois que vous corrigez Claude sur un point de convention, demandez-vous : « est-ce que cela devrait être dans le CLAUDE.md ? » Si la réponse est oui deux fois de suite, ajoutez-la. Voir aussi la page Memory de la documentation.

5. Commandes slash et commandes personnalisées

Intermédiaire

Les commandes slash pilotent la session elle-même. Les plus utilisées au quotidien :

CommandeQuand s'en servir
/helpRetrouver la liste complète des commandes
/initCréer le CLAUDE.md initial d'un projet
/clearChanger de sujet : on repart d'un contexte propre
/compactCondenser une longue session tout en gardant l'essentiel
/modelBasculer vers un modèle plus (ou moins) puissant
/permissionsVoir et modifier les autorisations en cours
/agentsGérer les sous-agents du projet (leçon 9)
/mcpInspecter les serveurs MCP connectés (leçon 9)

/clear mérite une mention particulière : contrairement à l'intuition, garder une session ouverte toute la journée dégrade la qualité. Le contexte se remplit de fichiers et de raisonnements sans rapport avec la tâche en cours. Un /clear entre deux sujets vaut mieux qu'un long fil.

Vos propres commandes. Tout fichier Markdown déposé dans .claude/commands/ devient une commande slash du projet. Le nom du fichier donne le nom de la commande : .claude/commands/revue.md crée /revue.

---
description: Revue de la modification en cours avant commit
argument-hint: [périmètre optionnel]
---

Effectue une revue du diff courant$ARGUMENTS.

Procédure :
1. Exécute `git diff` puis `git diff --staged`.
2. Pour chaque fichier modifié, vérifie :
   - respect des conventions du CLAUDE.md ;
   - gestion des cas d'erreur et des valeurs nulles ;
   - présence de tests pour tout nouveau comportement ;
   - absence de secret, de clé ou d'URL interne en dur.
3. Classe les remarques en : Bloquant / À corriger / Suggestion.
4. Ne modifie AUCUN fichier : produis uniquement le rapport.

Le marqueur $ARGUMENTS reçoit ce que vous tapez après la commande : /revue src/domain/. L'en-tête description s'affiche dans la liste des commandes ; argument-hint documente l'usage attendu.

Placez ces fichiers dans le dépôt et toute l'équipe hérite des mêmes commandes. Les vôtres, personnelles et valables partout, vont dans ~/.claude/commands/. La référence complète est la page Slash commands.

6. Permissions et sécurité

Intermédiaire

Claude Code demande votre accord avant toute action à effet de bord : modifier un fichier, exécuter une commande, appeler un outil externe. Ce dialogue est la principale barrière de sécurité — il se règle, il ne se contourne pas.

Les modes de permission définissent le niveau de friction :

ModeComportementUsage recommandé
defaultDemande à chaque action à effet de bordLe réglage normal, y compris pour les experts
planAnalyse et propose un plan, sans rien modifierExplorer un projet, préparer un gros chantier
acceptEditsAccepte automatiquement les modifications de fichiersTâches répétitives, sur un dépôt propre et commité
bypassPermissionsNe demande plus rienEnvironnement jetable et isolé uniquement

Pour éviter de répondre cent fois à la même question, déclarez une liste d'autorisations dans .claude/settings.json (versionné, partagé) ou .claude/settings.local.json (personnel, à ignorer dans git) :

{
  "permissions": {
    "allow": [
      "Bash(pnpm test:*)",
      "Bash(pnpm lint)",
      "Bash(git status)",
      "Bash(git diff:*)",
      "Read(src/**)",
      "Edit(src/**)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./secrets/**)",
      "Bash(curl:*)",
      "Bash(rm -rf:*)"
    ]
  }
}

La logique est celle du moindre privilège : on autorise ce qui est lu ou exécuté tous les jours et sans danger, on refuse explicitement ce qui touche aux secrets et au réseau.

Ce qu'il ne faut jamais autoriser aveuglément :

  • Les commandes destructrices non ciblées (rm -rf, DROP TABLE, réinitialisations de base).
  • git push, les déploiements, tout ce qui sort de votre machine.
  • Les commandes réseau arbitraires (curl, wget) qui exfiltrent ou téléchargent du code.
  • La lecture des fichiers de secrets : .env, clés SSH, jetons d'API.
  • Tout accès à un environnement de production, sous quelque forme que ce soit.
⚠️ Injection de prompt Claude Code lit du contenu que vous n'avez pas écrit : dépendances, tickets, pages web, sorties d'outils. Ce contenu peut contenir des instructions malveillantes. C'est précisément pourquoi les permissions existent : elles limitent les dégâts d'une instruction que vous n'avez jamais donnée. Détails sur la page Settings.

7. Travailler avec git

Intermédiaire

Git est le filet de sécurité de tout travail avec un agent : tant que votre travail est commité, aucune modification n'est irréversible. Prenez l'habitude de commencer une session sur un arbre de travail propre — git status vide. Vous saurez ainsi exactement ce que Claude a changé.

Travailler sur une branche. Pour toute tâche non triviale :

Crée une branche `feat/pagination-factures`, puis implémente
la pagination sur GET /factures (paramètres `page` et `taille`,
taille par défaut 20, maximum 100). Ajoute les tests.

Des commits propres. Claude rédige de bons messages de commit s'il comprend l'intention ; encore faut-il le lui demander :

Découpe ce travail en commits atomiques : un commit par intention,
avec un message en français au format « type(portée) : sujet ».
Le corps explique le POURQUOI, pas le comment.
Ne commite rien tant que `pnpm test` ne passe pas.

Relire les diffs. C'est le moment de vérité, et il ne se délègue pas. Un flux qui marche :

Montre-moi `git diff --staged`, puis explique fichier par fichier
ce que change ce diff et pourquoi. Signale toi-même ce qui te
semble discutable ou hors périmètre.

Faire expliquer son propre diff par Claude fait remonter des choses utiles : modifications collatérales, hypothèses prises faute d'instruction, code mort laissé derrière.

Résoudre des conflits. Claude Code est à l'aise sur les conflits de fusion, à condition de lui donner l'intention des deux côtés :

`git merge main` produit des conflits dans src/domain/facture.ts.
Côté main : la TVA est calculée dans le domaine.
Côté ma branche : j'ai extrait le calcul dans un service dédié.
Résous en gardant l'extraction, mais en reprenant la correction
d'arrondi venue de main. Puis lance les tests.

Ouvrir une pull request. Demandez une description qui sert à la relecture : contexte, ce qui change, ce qui ne change pas, comment tester, points d'attention pour le relecteur. Une PR bien décrite est relue deux fois plus vite.

✳ Le réflexe clé Commitez avant de lancer une tâche ambitieuse, jamais après coup. Un git stash ou un commit de sauvegarde coûte dix secondes ; reconstituer un travail écrasé coûte une matinée.

🟣 Niveau pro

8. Hooks et automatisation

Pro

Un hook est une commande shell exécutée automatiquement à un moment précis du cycle de vie de la session. La différence avec une consigne dans CLAUDE.md est essentielle : une consigne peut être suivie, un hook s'exécute toujours. Tout ce qui est non négociable — formatage, tests, interdiction d'un fichier — appartient aux hooks.

Les principaux points d'accroche :

ÉvénementDéclenchementUsage type
PreToolUseAvant l'exécution d'un outilBloquer une action interdite, journaliser
PostToolUseAprès l'exécution d'un outilFormater le fichier modifié, relancer les tests
UserPromptSubmitÀ l'envoi de votre messageInjecter du contexte (branche, ticket courant)
StopQuand Claude termine sa réponseContrôle final, notification
SessionStartAu démarrage d'une sessionPréparer l'environnement, charger un état

Configuration dans .claude/settings.json :

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/format.sh"
          }
        ]
      }
    ]
  }
}

Le matcher filtre les outils concernés ; le script reçoit sur son entrée standard un objet JSON décrivant l'appel (dont le chemin du fichier touché) :

#!/usr/bin/env bash
# .claude/hooks/format.sh — formate le fichier qui vient d'être écrit
set -euo pipefail

fichier=$(jq -r '.tool_input.file_path // empty')
[ -z "$fichier" ] && exit 0
[ -f "$fichier" ] || exit 0

case "$fichier" in
  *.ts|*.tsx|*.js|*.json|*.css|*.md) npx prettier --write "$fichier" ;;
  *.py)                              ruff format "$fichier" ;;
esac
exit 0

N'oubliez pas de rendre le script exécutable (chmod +x). Le code de sortie porte la sémantique : 0 laisse passer ; un code non nul signale un problème et, sur PreToolUse, bloque l'action — le message d'erreur étant renvoyé à Claude, qui peut corriger le tir.

Trois règles d'or : gardez les hooks rapides (ils s'exécutent souvent), idempotents (ils peuvent se déclencher plusieurs fois), et silencieux en cas de succès. Et rappelez-vous qu'un hook s'exécute avec vos droits : relisez-le comme du code de production. Référence : page Hooks.

9. MCP et sous-agents

Pro

Les serveurs MCP étendent ce que Claude Code peut atteindre : suivi de tickets, base de données, documentation interne, outils maison. Le protocole a été présenté au module 4 ; côté Claude Code, l'ajout se fait en une commande :

# Serveur local lancé comme un processus
claude mcp add mon-outil -- npx -y @exemple/serveur-mcp

# Serveur distant
claude mcp add --transport sse suivi https://exemple.interne/mcp

# Vérifier, puis inspecter dans la session
claude mcp list

La portée compte : par défaut le serveur est enregistré pour vous seul ; l'ajouter au périmètre projet (option --scope project) le partage avec l'équipe via un fichier versionné. Dans la session, /mcp affiche l'état des connexions et les outils exposés. Traitez l'installation d'un serveur tiers comme une dépendance logicielle : elle mérite une revue.

Les sous-agents répondent à un autre problème : la dilution du contexte. Un sous-agent est un assistant spécialisé, avec ses propres instructions, ses propres outils et son propre contexte. Il travaille à part et ne rend que sa conclusion — la session principale reste concentrée.

On les définit dans .claude/agents/, un fichier Markdown par agent :

---
name: revue-de-code
description: Relit un diff et remonte bugs, régressions et écarts de
  convention. À utiliser proactivement après toute modification
  significative, et avant chaque commit.
tools: Read, Grep, Glob, Bash
model: sonnet
---

Tu es relecteur de code senior sur ce projet. Ton unique livrable
est un rapport de revue. Tu ne modifies JAMAIS un fichier.

Méthode :
1. Exécute `git diff` puis `git diff --staged` pour cerner le
   périmètre exact de la modification.
2. Lis les fichiers touchés dans leur intégralité, pas seulement
   les lignes du diff : le bug est souvent dans le contexte.
3. Vérifie, dans cet ordre :
   - correction : cas limites, valeurs nulles, erreurs non gérées,
     conditions de concurrence, effets de bord non voulus ;
   - sécurité : secret en dur, entrée non validée, requête
     construite par concaténation, journalisation de données
     personnelles ;
   - tests : tout nouveau comportement est-il couvert ?
   - conventions : conformité au CLAUDE.md du projet.

Format du rapport, par ordre de gravité :
- BLOQUANT — fichier:ligne — problème — correction proposée
- À CORRIGER — ...
- SUGGESTION — ...

Si tu ne trouves rien de bloquant, dis-le explicitement.
N'invente pas de remarques pour remplir le rapport.

La liste tools applique le moindre privilège : ce relecteur peut lire et chercher, mais n'a ni Edit ni Write — il lui est matériellement impossible de modifier votre code. C'est plus solide qu'une consigne en toutes lettres. La commande /agents permet de créer et gérer ces agents ; voir les pages MCP et Sub-agents.

10. Mode headless, CI et Agent SDK

Pro

Tout ce que vous faites interactivement peut être scripté. Le mode headless s'active avec -p (pour print) : Claude traite la demande, écrit sa réponse sur la sortie standard, et rend la main.

# Une question ponctuelle
claude -p "Résume les changements du dernier commit en 5 puces"

# Alimenté par un tube, avec une sortie exploitable par un script
git diff main...HEAD | claude -p "Relève les risques de régression
de ce diff. Réponds en JSON : [{gravite, fichier, probleme}]" \
  --output-format json

# Avec un périmètre d'outils restreint
claude -p "Lance la suite de tests et explique les échecs" \
  --allowedTools "Bash(pnpm test:*)" "Read"

Les usages classiques : relecture automatique dans un pre-commit, triage de tickets, génération de notes de version, migration de masse pilotée par une boucle shell. Deux précautions : en headless, personne ne surveille — restreignez les outils explicitement, et faites toujours produire un artefact relu par un humain (un commentaire, un rapport) plutôt qu'une action irréversible.

En intégration continue. Anthropic fournit une action GitHub qui permet de déclencher Claude Code sur un dépôt : relecture automatique des pull requests, réponse à une mention dans un commentaire, correction d'un test cassé. Le principe reste le même — la sortie est une proposition : un commentaire de revue ou une branche, jamais un merge automatique. La marche à suivre est décrite sur la page GitHub Actions. Points d'attention : la clé d'API vit dans les secrets du dépôt ; méfiez-vous des exécutions déclenchées par des contributeurs externes ; et posez une limite de tours pour éviter les boucles.

L'Agent SDK. Quand le besoin dépasse le scriptage, le SDK permet de construire vos propres agents sur la même boucle que Claude Code — outils, permissions, sous-agents, hooks — en TypeScript ou en Python :

npm install @anthropic-ai/claude-agent-sdk

C'est la brique pour un agent d'astreinte qui diagnostique une alerte, un agent de migration qui traite un dépôt entier, ou un assistant interne branché sur vos outils. La référence à jour est la page SDK, complétée par code.claude.com/docs.

⚠️ Prudence Un agent automatisé hérite des droits que vous lui donnez. En CI, appliquez la même discipline qu'à un compte de service : portée minimale, aucun accès à la production, journalisation systématique, et revue humaine avant toute fusion.

💪 Exercices pratiques

Exercice · Débutant

Installer Claude Code et lui faire expliquer un projet

Installez Claude Code, ouvrez-le sur un projet existant (le vôtre ou un dépôt public que vous clonez), et menez une session d'exploration en lecture seule : architecture, point d'entrée, parcours d'une fonctionnalité, dette technique visible.

Voir une démarche corrigée

1. Installation et lancement :

npm install -g @anthropic-ai/claude-code
cd ~/projets/le-projet-a-explorer
claude

Suivez l'authentification proposée au premier démarrage, puis tapez /help pour repérer les commandes disponibles.

2. La séquence d'exploration, du général au particulier :

Ne modifie aucun fichier de toute cette session.
Décris ce projet : à quoi il sert, quelle est sa pile technique,
quel est le point d'entrée, et comment on le lance en local.
Dessine l'architecture en texte : les dossiers principaux,
le rôle de chacun, et qui dépend de qui. Signale les endroits
où la séparation des responsabilités n'est pas respectée.
Prends la fonctionnalité la plus importante du projet et
raconte-moi son parcours complet, du point d'entrée jusqu'à
la persistance, en citant les fichiers et les fonctions.
Quelles sont les 5 zones de ce code où une modification serait
la plus risquée, et pourquoi ? Cite les fichiers.
Comment lance-t-on les tests ? Quelle est la couverture réelle,
et quelles parties critiques ne sont pas testées ?

3. La vérification. Prenez deux affirmations de Claude et allez les contrôler vous-même dans le code. C'est l'étape que tout le monde saute : elle vous apprend le taux de fiabilité réel sur votre base de code, et c'est cette calibration qui vous rendra efficace ensuite.

4. La capitalisation. Terminez par :

Sur la base de cette exploration, propose-moi le contenu d'un
CLAUDE.md pour ce projet. Ne l'écris pas encore : montre-le-moi.

Vous obtenez ainsi la matière du prochain exercice, et vous découvrez ce que Claude a réellement compris — ses erreurs dans ce brouillon sont très instructives.

Exercice · Intermédiaire

Écrire le CLAUDE.md d'un projet réel

Sur un projet que vous connaissez, lancez /init puis réécrivez le résultat. L'objectif n'est pas d'avoir un fichier, mais d'avoir le bon fichier : celui qui vous évitera de répéter vos consignes.

Voir la solution

Squelette commenté à adapter section par section :

# CLAUDE.md

## Le projet en trois lignes
<!-- À quoi sert ce projet, pour qui, et la pile technique.
     Mentionnez les dépôts voisins : Claude ne les voit pas. -->

## Commandes
<!-- LA section la plus rentable. Des commandes EXACTES,
     copiables telles quelles. Précisez les prérequis. -->
- Installer : `...`
- Lancer en local : `...`
- Tests (tous) : `...`
- Tests (un seul fichier) : `...`
- Lint / format : `...`
- Build de production : `...`

## Architecture
<!-- Les dossiers et LEUR RÔLE, pas la liste des fichiers.
     Surtout : les règles de dépendance entre couches, qui ne
     se devinent pas à la lecture d'un fichier isolé. -->
- `src/...` : ...
Règle : ... n'appelle jamais ... directement.

## Conventions
<!-- Uniquement ce que le linter n'applique PAS déjà.
     Chaque règle vient d'une erreur réellement constatée. -->
- Typage : ...
- Gestion des erreurs : ...
- Nommage des fichiers et des symboles : ...
- Emplacement et nommage des tests : ...
- Journalisation : ... (ne jamais journaliser de donnée personnelle)

## À faire avant de proposer un diff
<!-- Une check-list courte et vérifiable. -->
1. `lint` passe.
2. `test` passe.
3. Tout nouveau comportement est couvert par un test.
4. Aucun secret ni URL interne en dur.

## Pièges connus
<!-- Le trésor du fichier : ce qui fait perdre une demi-journée
     à chaque nouvel arrivant. -->
- ...
- Ne pas modifier `...` : code figé.

## Hors périmètre
<!-- Ce que Claude ne doit PAS toucher, et pourquoi. -->
- `migrations/` : jamais rétroactivement, toujours une migration neuve.
- `vendor/`, `generated/` : code généré, modifier la source.

Les quatre erreurs classiques. (1) Écrire un cours : Claude connaît le langage, il ne connaît pas vos choix. (2) Copier la liste des fichiers : elle sera fausse dans un mois, et Claude sait explorer. (3) Répéter ce que le linter applique déjà : du bruit. (4) Écrire des règles vagues (« écrire du code propre ») : inutilisable. Une bonne règle est vérifiable : « les montants sont des entiers en centimes ».

La méthode de mise au point. Ne cherchez pas la perfection au premier jet. Travaillez une semaine normalement, et à chaque fois que vous corrigez Claude sur un point de convention, ajoutez la règle correspondante. Un raccourci utile : dans la session, une ligne commençant par # propose d'ajouter directement l'information à la mémoire du projet.

Le test de qualité. Ouvrez une session fraîche (/clear) et demandez :

À partir du seul CLAUDE.md, sans lire d'autre fichier :
comment lance-t-on les tests, où mettrais-tu un nouveau service
métier, et quelles sont les trois règles à ne jamais enfreindre ?

Si la réponse est juste, votre fichier est bon. Si elle est floue ou fausse, vous savez exactement quelle section réécrire. Enfin, versionnez ce fichier : c'est un document d'équipe, il se relit en revue de code comme le reste.

Exercice · Pro

Un sous-agent de revue de code et un hook de formatage

Équipez un projet de deux automatismes complémentaires : un sous-agent de revue qui ne peut pas modifier le code, et un hook qui formate automatiquement tout fichier écrit. Ajoutez une commande /revue pour appeler l'agent facilement.

Voir la solution

Arborescence cible :

.claude/
├── agents/
│   └── revue-de-code.md
├── commands/
│   └── revue.md
├── hooks/
│   └── format.sh
└── settings.json

1. .claude/agents/revue-de-code.md :

---
name: revue-de-code
description: Relit le diff courant et remonte bugs, failles et écarts
  de convention. À utiliser proactivement avant chaque commit et
  après toute modification significative.
tools: Read, Grep, Glob, Bash
model: sonnet
---

Tu es relecteur de code senior. Ton unique livrable est un rapport.
Tu ne modifies JAMAIS un fichier — même si on te le demande.

Méthode :
1. `git diff` puis `git diff --staged` pour cerner le périmètre.
2. Lis INTÉGRALEMENT les fichiers touchés : le bug est souvent
   dans le contexte, pas dans les lignes modifiées.
3. Relis le CLAUDE.md du projet avant de juger d'une convention.

Grille d'analyse, dans cet ordre :
- CORRECTION : cas limites, valeurs nulles, erreurs non gérées,
  concurrence, effets de bord, régressions sur l'existant.
- SÉCURITÉ : secret en dur, entrée non validée, requête construite
  par concaténation, journalisation de données personnelles,
  élévation de privilège.
- TESTS : tout nouveau comportement est-il couvert ? Les tests
  échouent-ils si l'on retire la correction ?
- CONVENTIONS : conformité au CLAUDE.md.
- LISIBILITÉ : nommage, fonction trop longue, code mort.

Format de sortie :
## Bloquant
- `fichier:ligne` — problème — correction proposée
## À corriger
- ...
## Suggestions
- ...
## Verdict
Une phrase : peut être commité / à reprendre.

Si rien n'est bloquant, dis-le franchement. N'invente aucune
remarque pour étoffer le rapport.

Le point clé : la ligne tools n'accorde ni Edit ni Write. L'agent est structurellement incapable de modifier le code ; on ne compte pas sur sa bonne volonté. Et son contexte séparé lui permet de lire des fichiers entiers sans encombrer la session principale.

2. .claude/commands/revue.md :

---
description: Lance une revue complète du travail en cours
argument-hint: [chemin optionnel]
---

Utilise le sous-agent `revue-de-code` sur le diff courant$ARGUMENTS.
Restitue son rapport tel quel, sans le résumer et sans corriger
toi-même les points remontés : j'arbitre ensuite.

3. .claude/hooks/format.sh (pensez à chmod +x) :

#!/usr/bin/env bash
# Formate le fichier qui vient d'être écrit ou modifié.
# Reçoit sur stdin le JSON décrivant l'appel d'outil.
set -euo pipefail

fichier=$(jq -r '.tool_input.file_path // empty')
[ -z "$fichier" ] && exit 0
[ -f "$fichier" ] || exit 0

case "$fichier" in
  */node_modules/*|*/vendor/*|*/generated/*) exit 0 ;;
esac

case "$fichier" in
  *.ts|*.tsx|*.js|*.jsx|*.json|*.css|*.md)
      npx --no-install prettier --write "$fichier" >/dev/null 2>&1 || true ;;
  *.py)
      command -v ruff >/dev/null && ruff format "$fichier" >/dev/null || true ;;
  *.go)
      command -v gofmt >/dev/null && gofmt -w "$fichier" || true ;;
esac

exit 0

4. .claude/settings.json qui relie le tout :

{
  "permissions": {
    "allow": [
      "Bash(git status)",
      "Bash(git diff:*)",
      "Bash(pnpm test:*)",
      "Bash(pnpm lint)",
      "Read(src/**)",
      "Edit(src/**)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./secrets/**)",
      "Bash(git push:*)",
      "Bash(curl:*)"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/format.sh"
          }
        ]
      }
    ]
  }
}

Choix de conception à justifier en entretien. Le hook se termine toujours par exit 0 et absorbe les erreurs du formateur : un outil absent ne doit pas bloquer la session. Il exclut node_modules et le code généré, qu'il serait absurde de reformater. Il est idempotent : le relancer dix fois donne le même fichier. Enfin, la séparation des rôles est nette — le hook applique ce qui est mécanique et non négociable (le format), le sous-agent produit ce qui relève du jugement (la revue), et c'est vous qui arbitrez. Vouloir faire corriger automatiquement les remarques de revue par un agent est précisément l'erreur à éviter : vous perdriez le seul moment où un humain regarde le code.

Pour aller plus loin : ajoutez un hook PreToolUse qui refuse toute écriture dans migrations/, et une commande /pr qui enchaîne revue, tests et rédaction de la description de pull request.

❓ Quiz de validation

Validez vos acquis — une seule bonne réponse par question.

1. Quelle commande installe Claude Code ?

L'installation de référence passe par npm en global. On se place ensuite à la racine d'un projet et l'on lance claude : le répertoire courant définit le périmètre d'exploration.

2. À quoi sert le fichier CLAUDE.md ?

Il est chargé automatiquement à chaque session. On y met les commandes exactes, les règles non devinables depuis le code et les pièges connus. /init en génère un premier jet, qu'il faut ensuite réécrire et maintenir.

3. Comment crée-t-on une commande slash personnalisée pour un projet ?

.claude/commands/revue.md crée /revue. Le marqueur $ARGUMENTS reçoit le texte tapé après la commande. Versionné dans le dépôt, le fichier profite à toute l'équipe.

4. Quelle est la différence essentielle entre une consigne du CLAUDE.md et un hook ?

Tout ce qui est non négociable — formatage, tests, interdiction d'écriture dans un dossier — appartient aux hooks. Le code de sortie porte la sémantique : non nul sur PreToolUse, l'action est bloquée et Claude en est informé.

5. Pourquoi ne pas donner les outils Edit et Write à un sous-agent de revue de code ?

Restreindre la liste tools applique le moindre privilège de façon structurelle, bien plus sûre qu'une consigne en toutes lettres. Le sous-agent dispose en outre de son propre contexte : il peut lire beaucoup sans encombrer la session principale.
