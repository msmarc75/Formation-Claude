Module 6

🔌 API & développeurs

L'API Anthropic, c'est Claude sans interface : une requête HTTP, une réponse, et tout ce que vous construisez autour. Ce module vous mène de la première requête à un pipeline de production — outils, streaming, documents, cache et traitement par lots.

Objectifs de ce module
  • Savoir quand l'API est le bon outil — et quand claude.ai suffit.
  • Obtenir une clé, la sécuriser et réussir sa première requête.
  • Maîtriser l'API Messages : rôles, streaming, outils, images et PDF.
  • Optimiser coût et fiabilité : prompt caching, Batch API, évaluations.

🟢 Niveau débutant

1. À quoi sert l'API — et quand la choisir

Débutant

Sur claude.ai, vous parlez à Claude. Avec l'API, c'est votre programme qui lui parle : votre code envoie une requête HTTP contenant des messages, Claude renvoie une réponse structurée, et votre application en fait ce qu'elle veut — l'afficher, la stocker, la transformer, déclencher une action.

Trois signaux indiquent qu'il faut passer à l'API :

  • Le volume : vous devez traiter 500 tickets, 10 000 fiches produit ou tous les e-mails d'une boîte partagée. Personne ne fera cela à la main dans un chat.
  • L'intégration : le résultat doit atterrir dans votre base de données, votre CRM, votre site — pas dans une fenêtre de conversation.
  • La répétabilité : la même consigne doit s'appliquer à l'identique, tous les jours, sans dépendre de la mémoire d'un humain.

À l'inverse, restez sur claude.ai (ou sur Cowork, module 4) quand la tâche est ponctuelle, exploratoire ou conversationnelle : rédiger une note, analyser un contrat, préparer une réunion. Écrire du code pour cela coûte plus cher que de le faire directement.

BesoinLa bonne porte
Réfléchir, rédiger, analyser un document ponctuelclaude.ai / Cowork
Automatiser une tâche répétitive sur un corpusAPI
Ajouter de l'IA dans un produit existantAPI
Travailler sur un dépôt de codeClaude Code (module 5)
Brancher Claude sur vos outils sans coderConnecteurs (module 7)

La facturation de l'API est indépendante de votre abonnement claude.ai : on paie à l'usage, par million de tokens consommés en entrée et en sortie. Les tarifs à jour figurent sur la page officielle des modèles.

💡 À retenir L'API ne rend pas Claude « plus intelligent » : c'est le même modèle. Elle vous donne le contrôle programmatique — et la responsabilité de tout le reste (prompt, contexte, erreurs, coûts).

2. Obtenir une clé API et la sécuriser

Débutant

Tout commence sur la console Anthropic : créez une organisation, ajoutez un moyen de paiement, puis générez une clé dans la section API keys. La clé n'est affichée qu'une seule fois — copiez-la immédiatement dans un gestionnaire de secrets.

Une clé API est un mot de passe qui coûte de l'argent. Quiconque la possède peut consommer votre budget. Quatre règles non négociables :

  1. Jamais dans le code. Pas de chaîne en dur, même « temporairement » : le temporaire finit toujours commité.
  2. Jamais dans git. Ajoutez .env à votre .gitignore avant le premier commit. Une clé poussée sur un dépôt public est compromise en quelques minutes.
  3. Jamais côté navigateur. Un appel à l'API depuis du JavaScript de page expose la clé à tous les visiteurs : passez toujours par votre serveur.
  4. Rotation régulière. Créez une clé par application et par environnement, révoquez-la dès qu'un doute existe, et faites tourner les clés périodiquement depuis la console.

En pratique, la clé vit dans la variable d'environnement ANTHROPIC_API_KEY, que les SDK lisent automatiquement :

# macOS / Linux — dans votre shell ou dans un fichier .env non versionné
export ANTHROPIC_API_KEY="votre-cle-ici"

# Vérification : la variable est-elle bien définie ?
printenv ANTHROPIC_API_KEY | head -c 8

# Ne jamais faire : git add .env
echo ".env" >> .gitignore
# En Python, on ne mentionne jamais la clé : le SDK la lit dans l'environnement
import anthropic

client = anthropic.Anthropic()  # lit ANTHROPIC_API_KEY

# En production, préférez un gestionnaire de secrets (Vault, AWS Secrets
# Manager, Google Secret Manager…) qui injecte la variable au démarrage.
⚠️ Prudence Une clé exposée se révoque en un clic dans la console — faites-le d'abord, enquêtez ensuite. Surveillez aussi la consommation par clé : une hausse inexpliquée est le premier symptôme d'une fuite.

Lire la réponse, champ par champ : content n'est pas une chaîne mais une liste de blocs typés (text, thinking, tool_use…) ; testez toujours block.type avant de lire block.text. stop_reason dit pourquoi Claude s'est arrêté : end_turn (fini), max_tokens (coupé, augmentez la limite), tool_use (il attend un outil), refusal (refus de sécurité). usage donne les tokens facturés, model le modèle qui a répondu, et id l'identifiant à journaliser pour tout support.

4. Anatomie d'une requête Messages

Intermédiaire

Tout passe par un seul point d'entrée, POST /v1/messages. Quatre champs structurent chaque appel :

  • model : l'identifiant exact du modèle (par exemple claude-opus-5 pour le raisonnement, claude-haiku-4-5 pour les tâches simples et massives).
  • max_tokens : obligatoire. C'est le plafond de la réponse, pas du contexte. Trop bas, la réponse est tronquée (stop_reason: "max_tokens").
  • system : un paramètre séparé, jamais un message de la liste. Il porte le rôle, les règles et le format attendu.
  • messages : la conversation, sous forme de liste alternant les rôles user et assistant. Le premier message est toujours user.

L'API est sans mémoire : elle ne conserve rien entre deux appels. Pour une conversation multi-tours, c'est à vous de renvoyer tout l'historique à chaque fois.

import anthropic

client = anthropic.Anthropic()
SYSTEME = "Tu es un assistant juridique. Tu cites toujours l'article invoqué."
historique = []

def echanger(question: str) -> str:
    historique.append({"role": "user", "content": question})
    response = client.messages.create(
        model="claude-opus-5",
        max_tokens=2048,
        system=SYSTEME,          # paramètre séparé, hors de `messages`
        messages=historique,     # tout l'historique, à chaque appel
    )
    reponse = "".join(b.text for b in response.content if b.type == "text")
    historique.append({"role": "assistant", "content": reponse})
    return reponse

print(echanger("Qu'est-ce qu'une clause de non-concurrence ?"))
print(echanger("Et sa durée maximale ?"))  # Claude comprend « sa » grâce à l'historique

Et la température ? Historiquement, temperature réglait le caractère aléatoire de la génération. Sur les modèles Claude récents (génération 4.6 et suivantes, dont claude-opus-5), les paramètres d'échantillonnage ont été retirés : on pilote désormais l'effort de réflexion avec output_config={"effort": "low" | "medium" | "high" | "xhigh" | "max"}, combiné à la réflexion adaptative thinking={"type": "adaptive"}. temperature reste disponible sur les modèles antérieurs comme claude-haiku-4-5. Vérifiez toujours ce que votre modèle accepte dans la référence de l'API.

5. Le streaming

Intermédiaire

Par défaut, l'API attend que la réponse soit entièrement générée avant de vous la renvoyer. Pour une réponse de 2 000 mots, cela fait plusieurs dizaines de secondes d'écran figé. Le streaming renvoie le texte au fil de sa production, sous forme d'événements successifs.

Deux raisons de l'utiliser :

  • L'expérience utilisateur : le texte qui s'écrit progressivement supprime la sensation d'attente — c'est le comportement de claude.ai.
  • La robustesse : sur les réponses longues (max_tokens élevé), une requête classique peut atteindre le délai d'expiration HTTP. Les SDK exigent d'ailleurs le streaming au-delà d'un certain volume.
import anthropic

client = anthropic.Anthropic()

with client.messages.stream(
    model="claude-opus-5",
    max_tokens=8000,
    system="Tu écris un français clair, sans jargon.",
    messages=[{"role": "user", "content": "Rédige un guide de 800 mots sur la sauvegarde des données."}],
) as stream:
    for texte in stream.text_stream:
        print(texte, end="", flush=True)

    # Le message complet reste accessible une fois le flux terminé
    final = stream.get_final_message()
    print(f"\n\n[{final.usage.output_tokens} tokens de sortie]")
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

const stream = client.messages
  .stream({
    model: "claude-opus-5",
    max_tokens: 8000,
    messages: [{ role: "user", content: "Rédige un guide de 800 mots sur la sauvegarde des données." }],
  })
  .on("text", (texte) => process.stdout.write(texte));

const final = await stream.finalMessage();
console.log(`\n[${final.usage.output_tokens} tokens de sortie]`);

En HTTP brut, il suffit d'ajouter "stream": true au corps de la requête : la réponse devient un flux Server-Sent Events avec les événements message_start, content_block_delta (le texte, morceau par morceau), message_delta (qui porte stop_reason et l'usage) puis message_stop.

💡 Bon réflexe Même quand vous n'affichez rien en direct, le streaming est une bonne assurance contre les délais d'expiration : lancez stream() et récupérez simplement get_final_message() à la fin.

6. Le tool use : donner des outils à Claude

Intermédiaire Premium

Un modèle de langage ne sait ni consulter votre base de données, ni appeler une API météo, ni calculer de façon exacte. Le tool use comble ce vide : vous décrivez des fonctions, Claude décide quand les appeler, votre code les exécute et lui renvoie le résultat.

Un outil se décrit par trois éléments : un name, une description (c'est elle qui détermine si Claude s'en sert — soyez explicite sur le quand) et un input_schema au format JSON Schema. La boucle est toujours la même : appel → stop_reason: "tool_use" → exécution → renvoi d'un bloc tool_result portant le même tool_use_id → nouvel appel, jusqu'à end_turn.

6. Le tool use : donner des outils à Claude

Intermédiaire

Un modèle de langage ne sait ni consulter votre base de données, ni appeler une API météo, ni calculer de façon exacte. Le tool use comble ce vide : vous décrivez des fonctions, Claude décide quand les appeler, votre code les exécute et lui renvoie le résultat.

Un outil se décrit par trois éléments : un name, une description (c'est elle qui détermine si Claude s'en sert — soyez explicite sur le quand) et un input_schema au format JSON Schema. La boucle est toujours la même : appel → stop_reason: "tool_use" → exécution → renvoi d'un bloc tool_result portant le même tool_use_id → nouvel appel, jusqu'à end_turn.

import json
import anthropic

client = anthropic.Anthropic()

OUTILS = [{
    "name": "obtenir_meteo",
    "description": (
        "Renvoie la météo actuelle d'une ville. "
        "À utiliser dès qu'une question porte sur le temps qu'il fait."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "ville": {"type": "string", "description": "Nom de la ville, par exemple Lyon."},
            "unite": {"type": "string", "enum": ["celsius", "fahrenheit"]},
        },
        "required": ["ville"],
    },
}]

def obtenir_meteo(ville: str, unite: str = "celsius") -> str:
    # Ici, appelez votre vraie source de données. Valeur simulée pour l'exemple :
    return json.dumps({"ville": ville, "temperature": 12, "unite": unite, "ciel": "averses"})

messages = [{"role": "user", "content": "Quel temps fait-il à Lyon ? Dois-je prendre un parapluie ?"}]

while True:
    response = client.messages.create(
        model="claude-opus-5",
        max_tokens=2048,
        tools=OUTILS,
        messages=messages,
    )
    messages.append({"role": "assistant", "content": response.content})

    if response.stop_reason != "tool_use":
        break

    resultats = []
    for bloc in response.content:
        if bloc.type == "tool_use":
            sortie = obtenir_meteo(**bloc.input)
            resultats.append({
                "type": "tool_result",
                "tool_use_id": bloc.id,   # doit correspondre au bloc tool_use
                "content": sortie,
            })
    # Tous les résultats repartent dans UN SEUL message user
    messages.append({"role": "user", "content": resultats})

print(next(b.text for b in response.content if b.type == "text"))

Deux pièges classiques : renvoyer les résultats de plusieurs outils dans des messages séparés (Claude cesse alors de paralléliser ses appels), et oublier de répondre à un outil qui a échoué — il faut renvoyer un tool_result avec "is_error": True et un message explicite. La documentation du tool use détaille les variantes (outils serveur, exécution de code, sorties structurées).

7. Vision et documents

Intermédiaire

Un message n'est pas forcément du texte : le champ content accepte une liste de blocs, dont des image (PNG, JPEG, GIF, WebP) et des document (PDF). Claude lit alors la mise en page, les tableaux, les graphiques et le texte manuscrit — ce qui en fait un excellent moteur d'extraction sur des documents scannés.

Cas d'usage typique : transformer une pile de factures numérisées en lignes de tableur. On combine deux techniques — le bloc document pour le PDF, et les sorties structurées (output_config) pour garantir un JSON conforme à un schéma, directement exploitable.

import base64
import json
import anthropic

client = anthropic.Anthropic()

with open("facture_scannee.pdf", "rb") as f:
    pdf_b64 = base64.standard_b64encode(f.read()).decode("utf-8")

response = client.messages.create(
    model="claude-opus-5",
    max_tokens=2048,
    messages=[{
        "role": "user",
        "content": [
            {
                "type": "document",
                "source": {
                    "type": "base64",
                    "media_type": "application/pdf",
                    "data": pdf_b64,
                },
            },
            {"type": "text", "text": "Extrais les données de cette facture. Si un champ est absent, mets une chaîne vide."},
        ],
    }],
    output_config={
        "format": {
            "type": "json_schema",
            "schema": {
                "type": "object",
                "properties": {
                    "numero": {"type": "string"},
                    "date": {"type": "string"},
                    "fournisseur": {"type": "string"},
                    "montant_ttc": {"type": "number"},
                },
                "required": ["numero", "date", "fournisseur", "montant_ttc"],
                "additionalProperties": False,
            },
        }
    },
)

texte = next(b.text for b in response.content if b.type == "text")
facture = json.loads(texte)
print(facture["fournisseur"], facture["montant_ttc"])

Quelques règles pratiques : placez le bloc image ou document avant le texte de la consigne ; la chaîne base64 ne doit contenir aucun retour à la ligne ; une requête reste plafonnée en taille et en nombre de pages. Pour un fichier réutilisé dans plusieurs requêtes, passez par l'API Files et référencez-le par son file_id plutôt que de le réenvoyer à chaque fois.

⚠️ Prudence Sur des documents à enjeu (comptabilité, santé, juridique), l'extraction automatique se contrôle : recoupez les totaux, journalisez les extractions douteuses et prévoyez une revue humaine par échantillon.

8. Prompt caching et optimisation des coûts

Pro Premium

Beaucoup d'applications renvoient à chaque requête un contexte identique : un long prompt système, un référentiel produit, une base de connaissances, une liste d'outils. Le prompt caching permet à l'API de mémoriser ce préfixe : les requêtes suivantes le relisent depuis le cache, à une fraction du coût des tokens d'entrée et avec une latence nettement réduite.

Le mécanisme repose sur une correspondance de préfixe exacte. L'ordre de composition est : tools, puis system, puis messages. Le moindre octet modifié avant le point de rupture invalide tout ce qui suit. D'où la règle d'architecture : le stable d'abord, le variable ensuite.

8. Prompt caching et optimisation des coûts

Pro

Beaucoup d'applications renvoient à chaque requête un contexte identique : un long prompt système, un référentiel produit, une base de connaissances, une liste d'outils. Le prompt caching permet à l'API de mémoriser ce préfixe : les requêtes suivantes le relisent depuis le cache, à une fraction du coût des tokens d'entrée et avec une latence nettement réduite.

Le mécanisme repose sur une correspondance de préfixe exacte. L'ordre de composition est : tools, puis system, puis messages. Le moindre octet modifié avant le point de rupture invalide tout ce qui suit. D'où la règle d'architecture : le stable d'abord, le variable ensuite.

import anthropic

client = anthropic.Anthropic()

REFERENTIEL = open("base_de_connaissances.md", encoding="utf-8").read()  # long et stable

def repondre(question: str):
    return client.messages.create(
        model="claude-opus-5",
        max_tokens=1024,
        system=[
            {"type": "text", "text": "Tu réponds uniquement à partir du référentiel fourni."},
            {
                "type": "text",
                "text": REFERENTIEL,
                "cache_control": {"type": "ephemeral"},  # point de rupture du cache
            },
        ],
        messages=[{"role": "user", "content": question}],  # partie variable : après le cache
    )

r1 = repondre("Quelle est la procédure de retour ?")
print(r1.usage.cache_creation_input_tokens)  # 1re requête : écriture du cache
r2 = repondre("Et pour un produit hors garantie ?")
print(r2.usage.cache_read_input_tokens)      # requêtes suivantes : lecture du cache

Ce qu'on met en tête : instructions figées, référentiel documentaire, exemples de référence, définitions d'outils dans un ordre déterministe. Ce qu'on met après : la question de l'utilisateur, l'horodatage, l'identifiant de session, tout ce qui change.

Le diagnostic est simple : si cache_read_input_tokens reste à zéro sur des requêtes censées partager un préfixe, un invalidateur silencieux est à l'œuvre — un datetime.now() dans le prompt système, un JSON sérialisé sans tri des clés, une liste d'outils construite dans un ordre aléatoire. Un préfixe trop court (quelques centaines de tokens) n'est simplement pas mis en cache. Détails dans la documentation du prompt caching.

9. Traitement par lots — la Batch API

Pro Premium

Quand le travail n'est pas interactif — classer un an d'archives, enrichir un catalogue, résumer des milliers de comptes-rendus — rien n'oblige à attendre chaque réponse. La Batch API accepte un lot de requêtes, les traite de façon asynchrone et applique une réduction de 50 % sur le coût des tokens, entrée et sortie comprises.

Le fonctionnement tient en trois temps : on crée le lot (chaque requête porte un custom_id), on interroge périodiquement son statut jusqu'à ended, puis on parcourt les résultats. La plupart des lots aboutissent en moins d'une heure, avec un plafond de 24 heures.

9. Traitement par lots — la Batch API

Pro

Quand le travail n'est pas interactif — classer un an d'archives, enrichir un catalogue, résumer des milliers de comptes-rendus — rien n'oblige à attendre chaque réponse. La Batch API accepte un lot de requêtes, les traite de façon asynchrone et applique une réduction de 50 % sur le coût des tokens, entrée et sortie comprises.

Le fonctionnement tient en trois temps : on crée le lot (chaque requête porte un custom_id), on interroge périodiquement son statut jusqu'à ended, puis on parcourt les résultats. La plupart des lots aboutissent en moins d'une heure, avec un plafond de 24 heures.

import time
import anthropic
from anthropic.types.message_create_params import MessageCreateParamsNonStreaming
from anthropic.types.messages.batch_create_params import Request

client = anthropic.Anthropic()

avis = ["Livraison rapide, produit conforme.", "Injoignable après achat.", "Correct sans plus."]

requetes = [
    Request(
        custom_id=f"avis-{i}",
        params=MessageCreateParamsNonStreaming(
            model="claude-haiku-4-5",
            max_tokens=16,
            system="Réponds par un seul mot : positif, negatif ou neutre.",
            messages=[{"role": "user", "content": texte}],
        ),
    )
    for i, texte in enumerate(avis)
]

lot = client.messages.batches.create(requests=requetes)

while True:
    lot = client.messages.batches.retrieve(lot.id)
    if lot.processing_status == "ended":
        break
    time.sleep(30)

resultats = {}
for r in client.messages.batches.results(lot.id):
    if r.result.type == "succeeded":
        message = r.result.message
        resultats[r.custom_id] = next(b.text for b in message.content if b.type == "text")
    else:
        resultats[r.custom_id] = f"ÉCHEC : {r.result.type}"

for cle in sorted(resultats):
    print(cle, "→", resultats[cle])

Deux points de vigilance. D'abord, les résultats arrivent dans un ordre quelconque : indexez-les par custom_id, jamais par position. Ensuite, chaque résultat porte son propre statut (succeeded, errored, canceled, expired) : un lot « terminé » peut contenir des échecs unitaires à rejouer. Le prompt caching se combine très bien avec les lots quand toutes les requêtes partagent un même préfixe. Référence complète : documentation du traitement par lots.

10. Agent SDK et mise en production

Pro

Un agent, c'est un modèle qui boucle : il observe, choisit un outil, agit, relit le résultat et recommence jusqu'à atteindre son objectif. Vous pouvez écrire cette boucle vous-même (leçon 6), la déléguer au tool runner du SDK, ou partir du Claude Agent SDK — un paquet distinct (claude-agent-sdk en Python, @anthropic-ai/claude-agent-sdk en TypeScript) qui fournit le harnais complet de Claude Code : outils de fichiers, exécution de commandes, sous-agents, permissions.

Mais l'essentiel de la mise en production n'est pas dans le choix du harnais. Trois chantiers font la différence :

1. Erreurs et reprises. Ne rattrapez pas une exception unique : distinguez le rejouable (429, 5xx, coupure réseau) du définitif (400, 404). Les SDK réessaient déjà avec un repli exponentiel ; réglez max_retries plutôt que de réinventer la boucle.

import logging
import anthropic

logging.basicConfig(level=logging.INFO)
client = anthropic.Anthropic(max_retries=4, timeout=120.0)

def appeler(messages):
    try:
        r = client.messages.create(model="claude-opus-5", max_tokens=4096, messages=messages)
    except anthropic.BadRequestError as e:
        logging.error("Requête invalide, ne pas rejouer : %s", e.message)
        raise
    except anthropic.RateLimitError:
        logging.warning("Quota atteint après les tentatives du SDK — mise en file d'attente.")
        raise
    except anthropic.APIConnectionError:
        logging.warning("Réseau indisponible — reprise différée.")
        raise

    logging.info(
        "req=%s modele=%s stop=%s in=%d out=%d",
        r._request_id, r.model, r.stop_reason,
        r.usage.input_tokens, r.usage.output_tokens,
    )
    if r.stop_reason == "max_tokens":
        logging.warning("Réponse tronquée : augmenter max_tokens.")
    return r

2. Journalisation. Conservez pour chaque appel l'identifiant de requête, le modèle, le stop_reason, les tokens consommés et la version de votre prompt. Sans cela, aucune analyse de coût ni aucun diagnostic n'est possible. Ne journalisez jamais la clé, ni des données personnelles non nécessaires.

3. Évaluations avant déploiement. Un prompt n'est pas du code : il n'a pas de test unitaire exact. Constituez un jeu de 30 à 100 cas représentatifs avec la sortie attendue, mesurez un taux de réussite, et rejouez-le à chaque changement de prompt, d'outil ou de modèle. C'est le seul garde-fou contre les régressions invisibles.

Première requête et effet des paramètres

Faites tourner votre première requête, puis observez concrètement deux réglages : faites varier max_tokens (16, 100, 1024) sur une consigne longue et regardez stop_reason ; puis faites varier temperature sur un modèle qui l'accepte et comparez deux exécutions identiques.

Voir la solution

Programme complet, à exécuter après pip install anthropic et export ANTHROPIC_API_KEY=… :

import anthropic

client = anthropic.Anthropic()
QUESTION = "Explique la photosynthèse à un enfant de 8 ans, avec une comparaison."

# 1) Effet de max_tokens : le plafond porte sur la RÉPONSE
for limite in (16, 100, 1024):
    r = client.messages.create(
        model="claude-opus-5",
        max_tokens=limite,
        messages=[{"role": "user", "content": QUESTION}],
    )
    texte = "".join(b.text for b in r.content if b.type == "text")
    print(f"--- max_tokens={limite} | stop_reason={r.stop_reason} "
          f"| sortie={r.usage.output_tokens} tokens")
    print(texte[:200], "…\n")

# 2) Effet de temperature : disponible sur les modèles antérieurs à la
#    génération 4.6 — ici claude-haiku-4-5.
for temp in (0.0, 1.0):
    sorties = []
    for _ in range(2):
        r = client.messages.create(
            model="claude-haiku-4-5",
            max_tokens=120,
            temperature=temp,
            messages=[{"role": "user", "content": "Donne un slogan pour une librairie."}],
        )
        sorties.append("".join(b.text for b in r.content if b.type == "text"))
    identiques = sorties[0] == sorties[1]
    print(f"--- temperature={temp} | deux exécutions identiques : {identiques}")
    print(sorties[0], "|", sorties[1], "\n")

# 3) Sur claude-opus-5, on ne règle plus temperature : on règle l'effort.
for effort in ("low", "high"):
    r = client.messages.create(
        model="claude-opus-5",
        max_tokens=2048,
        output_config={"effort": effort},
        thinking={"type": "adaptive"},
        messages=[{"role": "user", "content": "Combien de fenêtres à Paris ? Raisonne par ordres de grandeur."}],
    )
    print(f"--- effort={effort} | sortie={r.usage.output_tokens} tokens")

Ce que vous devez observer : à max_tokens=16, la réponse s'arrête en milieu de phrase et stop_reason vaut "max_tokens" — le modèle n'a pas « mal répondu », il a été coupé. À temperature=0.0, les deux exécutions sont quasi identiques ; à 1.0, elles divergent. Sur claude-opus-5, temperature serait rejetée : c'est effort qui module la profondeur de réflexion, et donc le nombre de tokens produits.

Exercice · Intermédiaire

Un outil de conversion de devises

Implémentez en tool use un outil convertir_devise qui prend un montant, une devise source et une devise cible, et renvoie le montant converti. Faites-le appeler par Claude sur la question : « J'ai 250 € et 300 $ : combien cela fait-il en livres au total ? » — ce qui exige deux appels d'outil.

Voir la solution complète

Le point clé est la boucle : tant que stop_reason vaut "tool_use", on exécute et on renvoie tous les résultats dans un seul message user.

import json
import anthropic

client = anthropic.Anthropic()

# Taux de démonstration. En production : appelez une vraie source, avec cache et date.
TAUX = {("EUR", "GBP"): 0.85, ("USD", "GBP"): 0.79, ("EUR", "USD"): 1.08}

OUTILS = [{
    "name": "convertir_devise",
    "description": (
        "Convertit un montant d'une devise vers une autre au taux du jour. "
        "À utiliser pour toute question impliquant deux devises. "
        "Un seul montant par appel : pour additionner plusieurs devises, "
        "appeler l'outil une fois par devise."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "montant": {"type": "number", "description": "Montant à convertir."},
            "source": {"type": "string", "description": "Code ISO de la devise d'origine, ex. EUR."},
            "cible": {"type": "string", "description": "Code ISO de la devise cible, ex. GBP."},
        },
        "required": ["montant", "source", "cible"],
        "additionalProperties": False,
    },
    "strict": True,
}]

def convertir_devise(montant: float, source: str, cible: str) -> str:
    source, cible = source.upper(), cible.upper()
    if source == cible:
        return json.dumps({"montant_converti": montant, "taux": 1.0})
    taux = TAUX.get((source, cible))
    if taux is None:
        inverse = TAUX.get((cible, source))
        taux = round(1 / inverse, 6) if inverse else None
    if taux is None:
        raise ValueError(f"Couple de devises non pris en charge : {source}/{cible}")
    return json.dumps({
        "montant_converti": round(montant * taux, 2),
        "devise": cible,
        "taux": taux,
    })

messages = [{
    "role": "user",
    "content": "J'ai 250 € et 300 $. Combien cela fait-il en livres au total ?",
}]

while True:
    response = client.messages.create(
        model="claude-opus-5",
        max_tokens=2048,
        system="Tu détailles toujours le calcul intermédiaire avant le total.",
        tools=OUTILS,
        messages=messages,
    )
    messages.append({"role": "assistant", "content": response.content})

    if response.stop_reason != "tool_use":
        break

    resultats = []
    for bloc in response.content:
        if bloc.type != "tool_use":
            continue
        try:
            contenu = convertir_devise(**bloc.input)
            erreur = False
        except Exception as e:            # l'échec d'un outil se RENVOIE, il ne se tait pas
            contenu = f"Erreur : {e}"
            erreur = True
        resultats.append({
            "type": "tool_result",
            "tool_use_id": bloc.id,
            "content": contenu,
            "is_error": erreur,
        })

    messages.append({"role": "user", "content": resultats})

print(next(b.text for b in response.content if b.type == "text"))

À observer : Claude émet deux blocs tool_use dans la même réponse (EUR→GBP et USD→GBP), que l'on exécute puis renvoie ensemble. La description de l'outil fait le gros du travail : c'est elle qui lui indique d'appeler la fonction une fois par devise. Le champ strict: True avec additionalProperties: false garantit que les arguments reçus respectent exactement le schéma.

Classifier 50 000 documents au meilleur coût

Une direction juridique veut classer 50 000 documents (environ 3 pages chacun) selon une taxonomie de 12 catégories, avec un niveau de confidentialité. Concevez le pipeline en optimisant le coût : choix du modèle, structure du prompt, mode d'exécution, contrôle qualité. Chiffrez l'ordre de grandeur en tokens.

Voir la solution

1. Estimation en tokens. 3 pages ≈ 1 500 mots ≈ 2 100 tokens. Ajoutez une consigne et une taxonomie stables d'environ 1 200 tokens, et une sortie JSON courte d'environ 60 tokens. Soit par document ≈ 3 300 tokens d'entrée et 60 de sortie ; sur 50 000 documents : ≈ 165 millions de tokens d'entrée et ≈ 3 millions de tokens de sortie. Ce seul calcul décide de l'architecture.

2. Choix du modèle. La classification sur taxonomie fermée est une tâche simple et massive : claude-haiku-4-5, la gamme la plus économique. On réserve un modèle plus puissant (claude-opus-5) aux seuls documents que le premier passage marque comme incertains — schéma « routeur + spécialiste ».

3. Prompt caching. La taxonomie, les règles et les exemples (≈ 1 200 tokens) sont identiques pour les 50 000 appels : on les place en tête de system avec un point de rupture de cache, le document venant après. Le préfixe stable est alors relu depuis le cache à une fraction du prix.

4. Batch API. Le travail n'est pas interactif : on soumet par lots, avec 50 % de réduction sur tous les tokens. Cumulé au cache, c'est l'essentiel de l'économie.

5. Sorties structurées + échantillon d'évaluation. On impose un JSON Schema pour éviter tout post-traitement fragile, et on annote à la main 200 documents avant le lancement pour mesurer le taux d'exactitude.

import json
import anthropic

TAXONOMIE = open("taxonomie.md", encoding="utf-8").read()  # stable : ~1200 tokens

]

    "type": "object",

    },

    "additionalProperties": False,
}

    return Request(
        custom_id=doc_id,
        params=MessageCreateParamsNonStreaming(
            model=modele,
            max_tokens=200,
            system=SYSTEME,
            messages=[{"role": "user", "content": texte}],   # partie variable : après le cache
            output_config={"format": {"type": "json_schema", "schema": SCHEMA}},
        ),
    )

❓ Quiz de validation

Validez vos acquis — une seule bonne réponse par question.

1. Quel paramètre est obligatoire dans toute requête à l'API Messages ?

max_tokens plafonne la longueur de la réponse et doit être fourni à chaque appel. S'il est trop bas, la réponse est tronquée et stop_reason vaut "max_tokens".

2. Où doit vivre votre clé API dans une application ?

Une clé en dur finit dans git ; une clé côté navigateur est lisible par tous les visiteurs. Variable d'environnement (ANTHROPIC_API_KEY) ou coffre de secrets, avec rotation régulière.

3. Comment transmet-on le prompt système ?

Le prompt système est un paramètre à part entière de la requête. La liste messages commence toujours par un message user et alterne user / assistant.

4. En tool use, que fait votre code quand stop_reason vaut "tool_use" ?

Claude décide quand appeler l'outil ; c'est votre programme qui l'exécute. Le résultat repart dans un message user, et tous les résultats d'un même tour tiennent dans un seul message.

5. Pour que le prompt caching fonctionne, où placer le contenu variable ?

Le cache fonctionne par correspondance de préfixe : un octet modifié invalide tout ce qui suit. Le stable d'abord (instructions, référentiel, outils), le variable ensuite (question, horodatage).
